# Где ведём задачи: GitHub

Задачи и описания требований для этого проекта живут в GitHub Issues. Все действия
выполняем через утилиту `gh` (официальная программа GitHub для командной строки).

## Как работать

- **Создать задачу**: `gh issue create --title "..." --body "..."`. Для многострочного
  текста удобнее передавать его через heredoc (способ вставить длинный текст прямо
  в команду).
- **Прочитать задачу**: `gh issue view <номер> --comments` — вместе с комментариями и
  метками.
- **Список задач**: `gh issue list --state open --json number,title,body,labels,comments --jq '[.[] | {number, title, body, labels: [.labels[].name], comments: [.comments[].body]}]'`, добавляя фильтры `--label` и `--state` по необходимости.
- **Написать комментарий**: `gh issue comment <номер> --body "..."`
- **Поставить или снять метку**: `gh issue edit <номер> --add-label "..."` и `--remove-label "..."`
- **Закрыть задачу**: `gh issue close <номер> --comment "..."`

Нужный репозиторий `gh` определяет сам по настройкам git, если запускать команды
внутри папки проекта.

## Считаем ли pull request'ы заявками

**Нет.** _(Если поменять на «да», разбор задач начнёт втягивать в общую очередь ещё и
pull request'ы от посторонних. Эту настройку читает навык разбора задач.)_

Pull request — это предложение изменений в коде от стороннего человека. В проектах с
открытым исходным кодом такое предложение часто и есть заявка на доработку. У нас
проект закрытый, посторонних участников нет, поэтому разбираем только задачи.

Если когда-нибудь понадобится включить, работает это так: у pull request'ов те же
метки и те же состояния, что у задач, только команды другие —

- **Прочитать**: `gh pr view <номер> --comments`, а `gh pr diff <номер>` покажет сами
  изменения в коде.
- **Список чужих pull request'ов**: `gh pr list --state open --json number,title,body,labels,author,authorAssociation,comments`, затем оставить только те, где `authorAssociation` равно `CONTRIBUTOR`, `FIRST_TIME_CONTRIBUTOR` или `NONE` (то есть отбросить свои и коллег — `OWNER`, `MEMBER`, `COLLABORATOR`).
- **Комментарий, метки, закрытие**: `gh pr comment`, `gh pr edit --add-label` и `--remove-label`, `gh pr close`.

Важная тонкость: у задач и pull request'ов в GitHub общая нумерация. Поэтому просто
«#42» может оказаться и тем и другим — проверяем через `gh pr view 42`, а если не
нашлось, то `gh issue view 42`.

## Если навык говорит «опубликовать в трекер задач»

Значит, создать задачу в GitHub Issues.

## Если навык говорит «взять нужную заявку»

Значит, выполнить `gh issue view <номер> --comments`.

## Работа с картой пути (wayfinder)

Навык `wayfinder` ведёт большие задумки как **карту** — одну задачу с меткой
`wayfinder:map`, к которой прицеплены дочерние задачи. Ниже — как это устроено
именно в GitHub.

### Найти карту

```bash
gh issue list --label "wayfinder:map" --state open --json number,title,url
```

### Дочерние задачи карты

Пользуемся штатным механизмом GitHub «под-задачи» (sub-issues) — тогда карта видна
в интерфейсе сама, без чтения текста.

Прицепить задачу к карте. Обратите внимание: нужен **внутренний числовой
идентификатор** задачи, а не её номер, и передавать его надо флагом `-F`, а не `-f`
(`-f` отправляет строку, и запрос будет отклонён):

```bash
ID=$(gh api repos/{owner}/{repo}/issues/<номер задачи> --jq .id)
gh api --method POST repos/{owner}/{repo}/issues/<номер карты>/sub_issues -F sub_issue_id=$ID
```

Посмотреть все дочерние задачи карты:

```bash
gh api repos/{owner}/{repo}/issues/<номер карты>/sub_issues --jq '.[] | "\(.number) \(.state) \(.title)"'
```

### Зависимости между задачами

Тоже штатный механизм GitHub — «заблокировано». Задача считается доступной, когда
все задачи, которых она ждёт, закрыты.

```bash
ID=$(gh api repos/{owner}/{repo}/issues/<кого ждём> --jq .id)
gh api --method POST repos/{owner}/{repo}/issues/<кто ждёт>/dependencies/blocked_by -F issue_id=$ID
```

Посмотреть, чего ждёт задача:

```bash
gh api repos/{owner}/{repo}/issues/<номер>/dependencies/blocked_by --jq '.[] | "\(.number) \(.state) \(.title)"'
```

### Граница — что можно брать прямо сейчас

Граница карты — это открытые дочерние задачи, которые никого не ждут и ни за кем не
закреплены. Готовой команды для этого нет, считается в два шага: взять дочерние
задачи, для каждой проверить зависимости и поле `assignee`.

```bash
MAP=<номер карты>
for n in $(gh api repos/{owner}/{repo}/issues/$MAP/sub_issues --jq '.[] | select(.state=="open") | .number'); do
  blockers=$(gh api repos/{owner}/{repo}/issues/$n/dependencies/blocked_by --jq '[.[] | select(.state=="open")] | length')
  who=$(gh api repos/{owner}/{repo}/issues/$n --jq '.assignee.login // "—"')
  [ "$blockers" = "0" ] && [ "$who" = "—" ] && gh issue view $n --json number,title --jq '"\(.number) \(.title)"'
done
```

### Взять задачу в работу

Закрепить за собой **до** начала работы, чтобы параллельные сессии её не взяли:

```bash
gh issue edit <номер> --add-assignee <логин>
```

Открытая и ни за кем не закреплённая задача считается свободной.

### Закрыть задачу

Ответ пишем комментарием, потом закрываем, потом дописываем строчку в раздел
«Решения на данный момент» в тексте карты:

```bash
gh issue comment <номер> --body "..."
gh issue close <номер>
gh issue edit <номер карты> --body-file <обновлённый текст карты>
```

### Как называть задачи в разговоре

В тексте для человека задачу называем **по названию**, а не по номеру. «Как устроена
геометрия помещения» читается с ходу, «#2» — нет. Номер и ссылка при этом никуда не
деваются, они прячутся внутрь названия-ссылки.
